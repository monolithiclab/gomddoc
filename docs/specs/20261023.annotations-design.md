# Design: Client-Side Page Annotations

**Date:** 2026-10-23
**Status:** Draft, awaiting validation. Questions settled 2026-10-23: feature toggle on by default, Vitest + a few
Playwright tests run only on front-end changes, canonical `CI_EXTRA` hook, repo-relative source path.

## Intent

The loop this serves: an LLM drafts a document (a spec, a plan) in a repository, the author reads it rendered by
gomddoc, and marks it up while reading. At the end of the review the author copies every note on the page as one
block of Markdown and pastes it into the LLM harness, which revises that same source file. The author then reloads
the page and reviews again.

So the export is written for a model, not a person: it must let the model find each passage in the source file and
act on the note without guessing.

## Goals

- Select text in a page, write a plain-text note on it, save or discard it.
- See annotated passages highlighted, with a margin icon per line; open a note from its icon, edit or delete it, and
  step through every note on that line.
- From a header button, read all notes of the page as editable Markdown, copy it, or clear every note (confirmed).
- Notes persist in the browser across reloads, per page.
- After the source changes, notes whose passage no longer matches are dropped, and the reader is told how many.
- On by default, behind a feature toggle; works in the default theme and the seven gomddoc-themes themes.

## Non-goals (first release)

- Any server side: no API, no storage on disk, no sharing between browsers or people.
- Rich text, replies, threads, authorship, timestamps in the export.
- Notes spanning several pages, a site-wide list of notes, or export of more than the current page.
- Annotating rendered math (KaTeX) or Mermaid diagrams.
- Mobile-specific interaction design beyond "it does not break" (see Builder's latitude).

## Anti-goals

- A note silently attached to the wrong passage after an edit. Dropping a note is acceptable; misplacing one is not.
- Touching the page's DOM structure in ways that break other shared scripts (code copy, heading anchors, TOC
  highlight, search) or change what `GET` returns for a page. Annotations are purely a browser overlay.
- A slow test suite, or one that runs when no front-end file changed.

## User experience

### Creating a note

1. The reader selects text inside the page content. When the selection is non-empty and lies entirely inside the
   annotatable content, a **pen button** appears in the right margin, level with the first line of the selection.
   Collapsing the selection or selecting outside the content hides it.
2. Clicking the pen (or a keyboard shortcut, see Accessibility) opens a **popover** next to it, holding a textarea
   with focus and two buttons: **Save** and **Discard**.
3. **Save** stores the note, highlights the passage and replaces the pen with a note icon. Saving an empty (or
   whitespace-only) note is a discard. **Discard**, `Esc` or a click outside closes the popover and stores nothing.
   `Ctrl/Cmd+Enter` saves.

### Existing notes

- Every stored note's passage is highlighted. A **note icon** sits in the right margin, level with the first line of
  the passage.
- Notes whose first lines sit on the same visual line share **one** icon showing their count. The popover opened
  from it shows one note at a time with **previous / next** controls and an "n of m" position, in document order.
- In an existing note's popover, the textarea holds its text. **Save** updates it (empty deletes it); **Delete**
  removes it; `Esc` or a click outside closes the popover and keeps the stored text unchanged. _(Builder's call
  recorded here: for an existing note, "discard" means "delete" only through the explicit Delete button.)_
- Icons are repositioned on resize and after fonts/late content load, so they stay level with their lines.

### The header button

- The header gains an **Annotations** button with a count badge (hidden at zero).
- It opens a dialog holding a textarea pre-filled with the export (below), editable, and three buttons: **Copy**
  (copies the textarea's current content, edits included, with a transient "Copied" confirmation), **Clear all**, and
  **Close**.
- **Clear all** asks for confirmation inside the dialog (a second, explicit confirm step; no `window.confirm`), then
  deletes every note of the page, removes highlights and icons, and empties the storage entry.
- With no notes, the dialog says so and Copy / Clear all are disabled.

### Stale notes

On load, each stored note is re-anchored (see Anchoring). Notes that no longer match are removed from storage, and a
short, dismissible notice says how many: "2 notes no longer match this page and were removed." Nothing is shown
when every note matches.

## Export format

Plain Markdown, notes in document order. Example:

```markdown
# Review notes: Client-Side Page Annotations

Source file: `specs/20261023.annotations-design.md`
Page: http://localhost:8080/specs/20261023.annotations-design

Each note quotes the passage it refers to, with the words just before and after it to disambiguate.

## 1. Intent › Goals

> …dropped, and the reader is told **how many**. On by default…

How many is "how many"? Give the exact wording of the notice.

## 2. User experience › The header button

> …gains an **Annotations** button with a count…

Call it "Review notes" instead.
```

- The heading per note is its position and the heading path of the section holding the passage (`H1 › H2 › H3`,
  nearest headings above it); "(top of page)" when no heading precedes it.
- The blockquote is `…{prefix}**{quote}**{suffix}…`, prefix and suffix being the context stored for anchoring,
  whitespace-collapsed. Markdown-significant characters in the quoted text are escaped so the bold markers stay
  unambiguous.
- The note body is the note text verbatim.
- **Source file** is the page's source path relative to the root of the git work tree holding the content root
  (`docs/specs/foo-design.md` for `gomddoc serve docs`), so the harness can open it from the repository root.
  Outside a git work tree it falls back to the path relative to the content root. Language directory included. It comes from the server (below); the URL alone is not enough because of
  `strip_extensions` and language prefixes.
- The leading heading uses the page title.

## Storage

- `localStorage`, one entry per page, key `gomddoc:annotations:` + `location.origin + location.pathname +
location.search`. The `#fragment` is excluded so TOC and heading-anchor clicks do not change the key.
- Value: `{"v": 1, "notes": [...]}`, each note `{id, quote, prefix, suffix, offset, note}`. `offset` is the passage's
  start in the content text when it was created (see Anchoring).
- An entry left empty is removed, not stored as an empty list.
- Storage that throws (private mode, quota, disabled) disables persistence for the session; the feature still works
  in memory and the notice says notes will not be kept. All reads and writes are wrapped.

## Anchoring

The text model is the concatenated text of the annotatable content element, **skipping** UI injected by scripts and
rendered content excluded from annotation: code-copy buttons, heading-anchor links, color-chip swatches, the
annotation UI itself, `.katex` and Mermaid output. Each skipped element is listed in one place in the module.

- **Create:** a selection becomes `{quote, prefix, suffix, offset}`: the selected text in that model, up to 32
  characters on each side, and its start offset. A selection may span skipped elements (a heading-anchor link, a copy
  button): their text is simply absent from the quote. A selection that starts or ends outside the model (inside a
  skipped element, or outside the content) is rejected (no pen shown).
- **Re-anchor:** search the text model for `prefix + quote + suffix`. Exactly one match: anchored. None, or several:
  stale, removed. No fuzzy matching and no tie-breaking in this release: when the original passage is deleted and an
  identical one remains elsewhere, choosing by position would move the note to the wrong passage (the anti-goal).
  _(Builder's call recorded here.)_ `offset` is kept to order notes and for a later tie-breaker.
- At the start or end of the content, prefix or suffix is shorter; it is still matched exactly.
- Re-anchoring runs once after `load`, so KaTeX, Mermaid and the other shared scripts have finished changing the
  DOM.

## Highlighting

Highlights use the **CSS Custom Highlight API** (`CSS.highlights`, `::highlight(gmd-annotation)`): ranges are
painted without wrapping text in elements, so the DOM other scripts and the text model read is untouched.
_(Builder's call recorded here.)_ It is supported by current Chrome, Safari and Firefox; where it is missing the
feature still works without highlights (icons and export stay correct).

Clicking highlighted text does nothing in this release; the margin icon is the entry point.

## Web platform

Nicolas asked (2026-10-23) for the UI to be built on current platform features (custom elements, the Popover API,
the `<dialog>` element) rather than `div`s carrying `data-*` attributes. The building blocks:

| Piece                | Built with                                                                                                                                                                                                                                                                                                                                                                     |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Content wrapper      | `<gmd-annotations>`, a light-DOM custom element around `{{ .Page.Content }}`. Light DOM because selection, the other shared scripts and theme CSS must see the content unchanged. It owns the controller: config, anchoring, highlights, store.                                                                                                                                |
| Pen and margin icons | `<gmd-annotation-margin>`, a shadow-DOM element rendering real `<button>`s, styled through `::part(pen)`, `::part(icon)` and the custom properties.                                                                                                                                                                                                                            |
| Note editor          | `<gmd-annotation-editor popover="auto">`: top layer (no clipping by `overflow` ancestors, no z-index contest), native light dismiss and `Esc`, opened with `showPopover({source})` so focus returns to its icon. Placed with CSS anchor positioning (`position-anchor`, `position-area`) where `CSS.supports("anchor-name: --a")`, with a small JavaScript fallback otherwise. |
| Header button        | `<gmd-annotations-toggle>`, a light-DOM element the theme puts in its header. It renders a `<button>` (so theme CSS for header buttons applies) that opens the dialog through Invoker Commands (`commandfor`, `command="show-modal"`), and shows the count. Hidden by `gmd-annotations-toggle:not(:defined)` until the module defines it.                                      |
| Notes dialog         | A native `<dialog>` owned by `<gmd-annotations>`, opened modally; `Esc` and focus return are native.                                                                                                                                                                                                                                                                           |
| Stale-notes notice   | `<gmd-annotation-notice popover="manual" role="status">`, top layer, dismissible.                                                                                                                                                                                                                                                                                              |
| Highlights           | CSS Custom Highlight API (above).                                                                                                                                                                                                                                                                                                                                              |

Elements talk through DOM events (`gmd-annotations-change` with the count, bubbling from `<gmd-annotations>` to
`document`), never through globals. The editor is a non-modal popover, so it does not trap focus: focus moves into its
textarea on open, `Tab` continues to the editor's buttons, and focus returns to the opener on close. Older browsers
without the Popover API or Invoker Commands are not supported by the annotation UI; the page itself still works.

## Server and theme changes

- **Feature toggle `annotations`**, default `true`, like every other key under `theme.features`: site config, env var
  `GOMDDOC_SITE_THEME_FEATURES_ANNOTATIONS`, per-page frontmatter override. No new config field; the existing
  features map carries it, and `gomddoc info` picks it up from the template scan.
- **Source path in the page context:** a `SourcePath` field on `PageContext`, set in `BuildPageContext` from what
  the pipeline resolved, for both `serve` and `build` (a directory index is its `README.md`/`index.md`; a page read
  from a git ref is the path inside the tree). Templates never derive it from the URL (AGENTS.md hard rule on
  URL/file mapping, in the other direction). It is emitted by gomddoc's own `scripts-shared` partial, in the
  module's configuration (a `<script type="application/json">` next to the module, also carrying the localized
  labels), **not** by themes: a theme using the new field would fail to render on older gomddoc releases.
- **Shared module** `cmd/gomddoc/assets/shared/gmd-annotations.mjs`, inlined by `scripts-shared` as
  `<script type="module">` when `.Feature "annotations"`, and its default styles via `inlineCSSAsset` (a new
  `gmd-annotations.css` shared asset) in the shared head. Theme colours come through CSS custom properties
  (`--gmd-annotation-highlight`, `--gmd-annotation-accent`, …) with defaults readable in light and dark mode.
- **Theme contract** (default theme and the seven gomddoc-themes themes, same release):
  - `{{ .Page.Content }}` is wrapped in `<gmd-annotations>…</gmd-annotations>` (content only, not tag chips, see-also
    or footer), only when the feature is on;
  - the header holds `<gmd-annotations-toggle></gmd-annotations-toggle>` where the theme sees fit, only when the
    feature is on.

  The contract uses no new template field, so an updated theme still renders on older gomddoc (where the elements
  stay undefined: the wrapper is inert and the toggle hidden). Order: gomddoc is tagged first, the themes follow.
  Nothing happens on a page without `<gmd-annotations>` (error pages, tag index pages).

- **Localization:** every visible string and ARIA label is a key in `cmd/gomddoc/assets/locales/en-US.yml`, reaching
  the module through the JSON configuration above. The export's fixed phrases ("Review notes", "Source file", "(top of page)") are localized
  too.

## Accessibility

- Pen, note icons, header button and dialog controls are real `<button>`s with localized labels; the note icon's
  label states its count.
- Keyboard: a shortcut (builder picks one that no shared script or major browser uses, documented in the guide)
  opens the popover for the current selection, so keyboard selection (`Shift`+arrows) can annotate. Note icons follow
  the page's other controls in the tab order: their layer is appended to `<body>`, outside any content column a theme
  clips with `overflow`, and the editor and dialog sit in the top layer, so the icons cannot sit next to the content
  in the DOM.
- The note editor (a non-modal popover) and the notes dialog (a modal `<dialog>`) close on `Esc` and return focus
  to the control that opened them; the dialog traps focus natively, the editor does not trap it (see Web platform).
- The stale-notes notice is announced (`role="status"`).
- Highlight colours meet WCAG AA contrast for the text over them in both colour schemes.
- `prefers-reduced-motion` disables any transition.

## Testing

All front-end tests live in a `web/` directory with its own `package.json` (pinned versions, lockfile committed).

- **Vitest** (`happy-dom` environment) carries most of the coverage. The module exports its pure parts (text model,
  selector creation, re-anchoring, line grouping, export formatting, storage read/write with a throwing storage) and
  does nothing until a `<gmd-annotations>` element connects, so importing it in a test has no side effect. Target: the
  whole Vitest suite under 5 seconds.
- **Playwright**, Chromium only, a handful of end-to-end tests against `gomddoc serve` on a small fixture site:
  create, edit, delete a note; two notes on one line and the previous/next controls; header dialog copy and clear
  all with confirmation; reload with an edited source drops a stale note and shows the notice; feature off renders
  no annotation markup. One `@axe-core/playwright` scan with the popover and the dialog open. Target: under 30
  seconds including server start.
- **Go tests:** `SourcePath` in `BuildPageContext`'s table test (serve and build, language pipeline, directory
  index, git provider); the default theme renders the attribute, button and JSON configuration with the feature on
  and none of them with it off. These guard the server side of the contract, which is why Go code is not an input to
  the `test-ui` hash below.
- **Runs only when front-end code changed.** `make test-ui` hashes the front-end inputs (`assets/shared/*.mjs` and
  `*.css`, the default theme's templates, the locale files, `web/` sources and lockfile) and compares with a stamp in `.cache/`; equal
  means skip, with a one-line message. When it must run and Node is missing, it fails with an install hint (never a
  silent skip). The hook is a canonical change in lab-standards: `common.go.mk` gains `CI_EXTRA ?=` and
  `ci: lint test $(CI_EXTRA)` (a no-op for fngr and musickit), and gomddoc sets `CI_EXTRA = test-ui`. So `make ci`
  stays the one gate; the macOS CI leg sets `CI_EXTRA=` and Playwright runs on ubuntu only. CI caches
  `.cache/` keyed on the same hash, so a push that touches no front-end file skips it there too. Playwright drives
  the system Chrome through its `chrome` channel, with no browser download; where Chrome is missing, the target fails
  with a one-line install hint.

The new third-party dependencies (Node toolchain, Vitest, happy-dom, Playwright, axe-core) are a recorded decision:
a new `D48` in `docs/decisions.md`. They are test-only and never reach the binary.
