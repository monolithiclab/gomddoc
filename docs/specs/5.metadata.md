# Metadata Specification - YAML Front Matter Support

## Overview

This specification details the implementation of YAML Front Matter support for gomddoc. This feature
allows Markdown files to define metadata (such as title, description, author, tags, etc.) in a YAML
block at the beginning of the file. This metadata will be parsed and exposed to the template engine,
allowing for richer and more customizable document presentation.

## Goals

1.  **Parse YAML Front Matter:** Extract and parse the YAML block delimited by `---` at the start of
    Markdown files.
2.  **Metadata Extraction:** Convert the parsed YAML into a structured format available to
    templates.
3.  **Graceful Fallbacks:** If metadata is missing or incomplete, fall back to sensible defaults
    (e.g., derive title from filename).
4.  **Template Integration:** Expose the metadata in the `PageContext` so themes can utilize it.
5.  **Performance:** Efficiently parse front matter without re-reading the entire file multiple
    times.

## Front Matter Syntax

The front matter must be the first thing in the file and must take the form of valid YAML set
between triple-dashed lines.

```markdown
---
title: "My Custom Title"
description: "A description of this page."
author: "Jane Doe"
tags: ["documentation", "spec"]
date: 2023-10-27
---

# Content starts here...
```

## Architecture Changes

### 1. Metadata Structure

We will define a new `PageMeta` struct to hold the parsed metadata. This struct will be part of the
`template` package or a new `metadata` package if it grows too large.

```go
// internal/template/metadata.go (proposed)

type PageMeta struct {
    Title       string   `yaml:"title"`
    Description string   `yaml:"description"`
    Author      string   `yaml:"author"`
    Date        string   `yaml:"date"` // Keep as string for flexibility, parse in template if needed
    Tags        []string `yaml:"tags"`
    // Allow arbitrary other fields
    Extra       map[string]interface{} `yaml:",inline"`
}
```

### 2. Renderer Update

The `MarkdownRenderer` needs to be updated to handle front matter. Currently, it passes the raw
content directly to the markdown parser.

**New Flow:**

1.  **Split:** `MarkdownRenderer.Render` receives the raw bytes. It checks if the file starts with
    `---`.
2.  **Extract:** If present, it extracts the YAML block and the remaining markdown content.
3.  **Parse:** The YAML block is unmarshaled into a `PageMeta` struct.
4.  **Render Content:** The _remaining_ markdown content is passed to the markdown parser
    (blackfriday/gomarkdown).
5.  **Return:** The renderer currently returns `([]byte, string, error)`. We need a way to pass this
    metadata back to the handler/template.

**Challenge:** The `ContentRenderer.Render` interface returns `([]byte, string, error)`. It returns
the _rendered HTML body_. It doesn't currently have a channel to return metadata.

**Solution Options:**

- **Option A: Return Metadata:** Change `Render` signature to return `([]byte, PageMeta, string,
error)`. This is a breaking change for the interface.
- **Option B: Context:** Pass a "Metadata Collector" in the context? Messy.
- **Option C: Double Parsing (Handler Level):** The Handler parses front matter _before_ calling
  Render.
  - _Pros:_ Keeps Renderer interface clean. Handler is responsible for "Page Context" assembly
    anyway.
  - _Cons:_ Handler needs to know about Markdown syntax (the `---` delimiters).
- **Option D (Selected):** Update `ContentRenderer` interface to return an optional `interface{}`
  for metadata.

**Decision:** We will modify the `ContentRenderer` interface. Since we are in early
development/refactoring (Phase 3/4), we can afford an interface tweak for such a core feature.

```go
// internal/renderer/renderer.go

type ContentRenderer interface {
    SupportedMimeTypes() []string
    // Returns: content, metadata, mimeType, error
    Render(ctx context.Context, content []byte) ([]byte, interface{}, string, error)
}
```

_Note:_ If we don't want to break the interface immediately, we can have `MarkdownRenderer`
implement an additional interface `MetadataExtractor` that the Handler checks for.

**Refined Decision:** To adhere to the "clean architecture" and avoid breaking the generic
`ContentRenderer` for all types (images don't have frontmatter), let's handle Front Matter
extraction in the **Renderer implementation** but return it via a side-channel or an enriched return
type.

Actually, the cleanest way is to return a `RenderResult` struct instead of multiple return values.

```go
type RenderResult struct {
    Content  []byte
    MimeType string
    Metadata map[string]interface{}`
}

type ContentRenderer interface {
    SupportedMimeTypes() []string
    Render(ctx context.Context, content []byte) (*RenderResult, error)
}
```

This is a **breaking change** but a necessary one for a robust CMS/SSG capabilities. It prepares us
for future needs (e.g., returning list of images found, links for validation, etc.).

### 3. Handler Logic

The `Handler` orchestrates the process.

1.  Call `provider.ReadFile` -> get raw bytes.
2.  Call `renderer.Render`.
3.  Receive `RenderResult`.
4.  Construct `template.PageContext`.
    - `PageContext.Content` = `RenderResult.Content`
    - `PageContext.Meta` = `RenderResult.Metadata` (merged with defaults)
5.  Call `templateRenderer.Render`.

### 4. Template Context Update

We need to expose this metadata to the templates.

```go
// internal/template/renderer.go

type PageContext struct {
    Content     template.HTML
    Breadcrumbs map[string]string
    Meta        map[string]interface{} // New field

    // Helper accessors for common fields (optional, can be done in template func)
    // Title string
    // Description string
}
```

### 5. Defaults and Fallbacks

The Handler (or a helper in `template` package) determines the final values.

- **Title:**
  1.  Front Matter `title`
  2.  First H1 header in markdown (parsing this is expensive, maybe skip for now)
  3.  `SiteConfig.Meta.Title` (Site title) ? No, page title should be specific.
  4.  Filename (formatted: `my-page.md` -> "My Page")
- **Description:**
  1.  Front Matter `description`
  2.  `SiteConfig.Meta.Description`

## Implementation Steps

### Step 1: Define Interfaces & Structs

- Update `ContentRenderer` interface to return a `RenderResult` struct.
- Update `PassthroughRenderer` to return empty metadata.
- Update `MarkdownRenderer` signature.

### Step 2: Implement Front Matter Parsing

- In `internal/renderer/markdown.go`:
  _ Add a function `parseFrontMatter(content []byte) ([]byte, map[string]interface{}, error)`.
  _ Use `bytes.HasPrefix(content, []byte("---\
"))` to detect.
  _ Find closing `---`.
  _ Use `gopkg.in/yaml.v3` to unmarshal the block.
  - Return the \*rest\* of the content as the body.

### Step 3: Update Handler

- Update `internal/server/handler.go` to handle the new `RenderResult`.
- Implement the default title logic (Filename to Title).
  - Helper function: `deriveTitle(filename string) string`.

### Step 4: Update Template Renderer

- Update `PageContext` struct.
- Update `internal/template/renderer.go` to populate `PageContext.Meta`.

### Step 5: Update Default Theme

- Update `assets/themes/default/layout.html.tmpl`.
- Use `{{ .Page.Meta.title }}` if available, else fall back.
- Ideally, the Handler should prepare a "final" `Title` string in the context so the template logic
  is simple: `{{ .Page.Title }}`.

## Logic for Default Title (Filename)

```go
func deriveTitle(path string) string {
    base := filepath.Base(path)
    ext := filepath.Ext(base)
    name := strings.TrimSuffix(base, ext)

    // Replace hyphens/underscores with spaces
    name = strings.ReplaceAll(name, "-", " ")
    name = strings.ReplaceAll(name, "_", " ")

    // Capitalize Title Case (simple version)
    return cases.Title(language.English).String(name)
}
```
