# CLI Subcommand Architecture

> **Status: Draft.** This spec designs the migration from flat flag-based CLI to a subcommand architecture.

## Motivation

The current CLI uses stdlib `flag` with flat flags (`-d`, `-p`, `-dev`, `-git-key-file`). As gomddoc grows
(build/export commands, validation, init scaffolding), a flat flag namespace becomes unwieldy. A subcommand
architecture provides:

- Clear separation of concerns per command
- Self-documenting help with exhaustive flag and env var listing
- Extensibility for future commands without flag collisions
- Industry-standard UX (`gomddoc serve`, `gomddoc init`, `gomddoc build`)

## Library Evaluation

### Option 1: Cobra (`github.com/spf13/cobra`)

**Pros:**
- Industry standard - used by Docker, Kubernetes, Hugo, GitHub CLI
- Excellent subcommand support with nested commands
- Built-in help/usage generation, shell completions, man page generation
- Massive community, comprehensive documentation
- Persistent flags (inherited by subcommands) vs local flags
- `cobra-cli` scaffolding tool for new commands

**Cons:**
- Imperative style: commands defined procedurally, flags registered via `cmd.Flags().StringVar()`
- Heavier dependency (~5 transitive deps including pflag)
- Does not natively show env var names in help output (requires custom usage template)
- Verbose boilerplate per command (~30-40 lines before any logic)
- Typically paired with Viper for env/config, adding another dependency

### Option 2: Kong (`github.com/alecthomas/kong`)

**Pros:**
- Declarative struct-tag approach - mirrors our existing `env:` tag pattern exactly
- Native env var support in tags: `env:"GOMDDOC_SERVER_PORT"` - shown automatically in `--help`
- Subcommands modeled as struct fields (type-safe, compile-time checked)
- Auto-generates exhaustive help including defaults, env vars, and types
- Minimal dependency footprint (zero transitive deps)
- Supports custom value mappers for `time.Duration`, custom types, etc.
- Excellent Go-idiomatic design

**Cons:**
- Smaller community than Cobra (though actively maintained, ~2k stars)
- Less ecosystem tooling (no shell completion generator built-in, though plugins exist)
- Struct-heavy approach can feel unfamiliar to developers used to Cobra

### Option 3: urfave/cli v3 (`github.com/urfave/cli/v3`)

**Pros:**
- Popular (~22k stars), well-maintained
- Good subcommand support
- Built-in env var support for flags
- Moderate learning curve

**Cons:**
- v3 is relatively recent, less battle-tested than v2
- More boilerplate than Kong, less than Cobra
- No struct-based definition (imperative flag registration)
- Not as Go-idiomatic as Kong

### Option 4: Standard Library (`flag` + custom routing)

**Pros:**
- Zero external dependencies
- Full control

**Cons:**
- Significant custom code for subcommand routing, help generation, env var display
- No auto-generated usage - must maintain help text manually
- Reinventing what libraries solve well
- Error-prone flag set management across subcommands

### Recommendation: Kong

Kong is the clear choice for gomddoc because:

1. **Natural fit**: gomddoc already uses struct tags (`env:"PORT"`, `yaml:"title"`) for configuration.
   Kong extends this pattern to CLI flags: one struct defines flags, env vars, defaults, and help text.

2. **Exhaustive help for free**: Kong auto-generates help output showing flag names, env vars, defaults,
   and descriptions - exactly what the spec requires. No custom templates needed.

3. **Minimal churn**: The existing `Config` struct hierarchy can be adapted in-place rather than
   rewritten. Kong populates structs directly, similar to how `yaml.Unmarshal` works today.

4. **Zero transitive deps**: Keeps the dependency tree lean (gomddoc values minimal dependencies).

5. **Type safety**: Subcommands are struct fields, so adding a new command is a compile-time checked
   change - not a runtime string registration.

## Design

### CLI Grammar

```
gomddoc [--version] [--help] <command> [<args>]

Commands:
  serve    Start the HTTP server to serve markdown files as HTML

Flags:
  --version    Show version and exit
  --help       Show help
```

```
gomddoc serve [flags]

Flags:
  -d, --dir=STRING           Markdown directory ($GOMDDOC_SERVER_DIR, default: ".")
  -p, --port=STRING          HTTP listen address ($GOMDDOC_SERVER_PORT, default: ":8080")
      --dev                  Enable development mode ($GOMDDOC_SERVER_DEV_MODE)
      --git-key-file=STRING  Path to SSH private key ($GOMDDOC_SERVER_GIT_SSH_KEY)
```

### Struct Definition

```go
// CLI is the top-level Kong command struct.
type CLI struct {
    Version kong.VersionFlag `name:"version" help:"Show version and exit."`
    Serve   ServeCmd         `cmd:"" help:"Start the HTTP server to serve markdown files as HTML."`
}
```

```go
// ServeCmd holds all flags for the serve subcommand.
type ServeCmd struct {
    Dir       string        `name:"dir" short:"d" default:"." env:"GOMDDOC_SERVER_DIR" help:"Markdown directory or Git URL."`
    Port      string        `name:"port" short:"p" default:":8080" env:"GOMDDOC_SERVER_PORT" help:"HTTP listen address (host:port)."`
    DevMode   bool          `name:"dev" default:"false" env:"GOMDDOC_SERVER_DEV_MODE" help:"Enable development mode (no caching, verbose logging)."`
    GitSSHKey string        `name:"git-key-file" env:"GOMDDOC_SERVER_GIT_SSH_KEY" help:"Path to SSH private key file for Git authentication."`
}

// Run executes the serve command.
func (s *ServeCmd) Run(globals *Globals) error {
    // Build config.Config from ServeCmd fields, then boot the server.
}
```

### Package Layout

```
cmd/gomddoc/
    main.go          # Kong parser setup, version injection, os.Exit
    serve.go         # ServeCmd definition and Run() method
    assets/          # (existing embedded assets, unchanged)
```

The `internal/config` package retains its role for:
- `Config` / `SiteConfig` structs (used internally by server, template, provider)
- YAML config file loading (`LoadFromFile`)
- Validation logic
- Dynamic defaults (`ComputeDynamicDefaults`)

Kong replaces only the **flag parsing and env var loading** responsibilities. The CLI structs in
`cmd/gomddoc/` act as the entry point, building a `config.Config` to pass downstream.

### Configuration Loading Order (Revised)

The current order is: Defaults -> Env -> Flags -> File -> Env -> Validate

With Kong, the order simplifies because Kong resolves flags and env vars in one pass
(flags > env > defaults):

```
1. Kong parses CLI          (resolves: flags > env vars > defaults)
2. Build config.Config      (from ServeCmd fields)
3. ComputeDynamicDefaults   (e.g., title from dir)
4. LoadFromFile             (.gomddoc/config.yml merges site-level settings)
5. Re-apply env overrides   (env > file for site config)
6. Validate                 (existing validation logic)
```

This preserves the existing precedence semantics while eliminating the manual `ApplyEnvOverrides()`
call for server-level settings (Kong handles it natively).

### Backward Compatibility

**Breaking change**: `gomddoc -d /path` becomes `gomddoc serve -d /path`.

Mitigation strategy - implement Kong's default command feature:

```go
type CLI struct {
    Serve ServeCmd `cmd:"" default:"withargs" help:"Start the HTTP server."`
}
```

With `default:"withargs"`, running `gomddoc -d /path` still works - Kong routes to `serve`
when no explicit subcommand is given. This makes the migration fully backward-compatible.

When a second command is added (e.g., `init`), the default can be reconsidered, but for now
it preserves existing behavior.

### Help Output Examples

**Root help** (`gomddoc --help`):
```
Usage: gomddoc <command> [flags]

A production-ready HTTP server that serves Markdown files as HTML.

Commands:
  serve    Start the HTTP server to serve markdown files as HTML (default)

Flags:
  --version    Show version and exit
  -h, --help   Show help
```

**Serve help** (`gomddoc serve --help`):
```
Usage: gomddoc serve [flags]

Start the HTTP server to serve markdown files as HTML.

Flags:
  -d, --dir=STRING            Markdown directory or Git URL ($GOMDDOC_SERVER_DIR, default: .)
  -p, --port=STRING           HTTP listen address ($GOMDDOC_SERVER_PORT, default: :8080)
      --dev                   Enable development mode ($GOMDDOC_SERVER_DEV_MODE)
      --git-key-file=STRING   Path to SSH private key file ($GOMDDOC_SERVER_GIT_SSH_KEY)
  -h, --help                  Show help
```

Note: Kong auto-generates the env var names and defaults in the help text from struct tags.

## Implementation Plan

### Step 1: Add Kong Dependency

```bash
go get github.com/alecthomas/kong
```

### Step 2: Create CLI Structs (`cmd/gomddoc/serve.go`)

Define `ServeCmd` with all current flags mapped to Kong struct tags. Include the `Run()` method
that builds a `config.Config` and executes the existing `startCmd()` logic.

### Step 3: Refactor `main.go`

Replace `flag`-based parsing with Kong:

```go
func main() {
    cli := CLI{}
    ctx := kong.Parse(&cli,
        kong.Name("gomddoc"),
        kong.Description("A production-ready HTTP server that serves Markdown files as HTML."),
        kong.Vars{"version": version}, // injected at build time
    )
    err := ctx.Run()
    if err != nil {
        slog.Error("Fatal error", slog.Any("error", err))
        os.Exit(1)
    }
}
```

### Step 4: Adapt `internal/config`

- Remove `ParseFlags()` method (Kong handles flag parsing)
- Remove server-level env var walking (Kong handles `GOMDDOC_SERVER_*` vars)
- Keep `SiteConfig.ApplyEnvOverrides()` for site-level env vars (loaded after YAML file)
- Keep `LoadFromFile()`, `Validate()`, `ComputeDynamicDefaults()` unchanged
- Add a constructor: `NewFromServeCmd(dir, port string, devMode bool, gitSSHKey string) *Config`

### Step 5: Update Tests

- `config_load_test.go`: Remove `flag.CommandLine` manipulation; test `NewFromServeCmd` directly
- Add CLI integration tests using Kong's test helpers (`kong.Must(&cli)` with args)
- Existing server/provider/renderer tests remain unchanged

### Step 6: Version Injection

Add `ldflags` version injection to `Makefile`:

```makefile
VERSION ?= $(shell git describe --tags --always --dirty 2>/dev/null || echo "dev")
LDFLAGS := -ldflags "-X main.version=$(VERSION)"

build:
    go build $(LDFLAGS) -o build/gomddoc ./cmd/gomddoc
```

## Future Commands (Out of Scope)

This spec only implements `serve`. Future candidates that motivate the subcommand architecture:

| Command | Purpose |
|---------|---------|
| `gomddoc init` | Scaffold a `.gomddoc/` directory with default config |
| `gomddoc build` | Static site generation (render all markdown to HTML files) |
| `gomddoc validate` | Validate config and check for broken links |
| `gomddoc themes` | List available themes or preview them |

Each command will be a new struct field on `CLI` with its own `Run()` method.

## Testing Strategy

1. **Unit tests**: Test `ServeCmd.Run()` with mock dependencies
2. **CLI integration tests**: Use `kong.Must()` to parse test args, verify flag/env/default resolution
3. **Backward compat test**: Verify `gomddoc -d /tmp -p :9000` still works (default command)
4. **Help output test**: Parse `--help` output to verify all flags and env vars are documented
5. **Existing tests**: All `internal/` package tests must pass unchanged
